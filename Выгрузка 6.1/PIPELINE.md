# BIM2VOR Pipeline — Событие 6.1

## Цель

Заполнить колонку 12 ("Количество ГП") в ВОР заказчика своими объёмами,
рассчитанными из 9 BIM-моделей. Объёмы заказчика (колонка 9) — для сравнения,
но **не для копирования**.

## Этап 1: Ingest (загрузка в SQLite)

**Скрипт:** `bim2vor/ingest/loader.py`

```
Excel (9 файлов) ──→ RevitReader (стриминг) ──→ SQLite (bim2vor.db)
```

### Что происходит:
1. Каждый Excel читается через `openpyxl` в режиме `read_only=True` (не грузит весь файл в память)
2. `RevitReader` парсит строки в объекты `Element` с полями: category, family, type_name, volume_m3, area_m2, length_m, level_raw и т.д.
3. Элементы пишутся в таблицу `elements` батчами по 5000 строк
4. Каждый элемент получает `source_model` (BA_AR, KR и т.д.) из имени файла
5. Физичность (`is_physical`) и исключения (`is_excluded`) определяются по OST-таксономии

### Результат:
- `runs/bim2vor.db` — SQLite база, таблица `elements`, 722 981 строка
- Из них ~248 748 физических неисключённых элементов

---

## Этап 2: Кластеризация (SQL)

**Скрипт:** `bim2vor/ingest/cluster_sql.py`

```
SQLite ──→ GROUP BY (category, family, type_name) ──→ Кластеры
```

### Что происходит:
SQL-запрос группирует элементы по трём полям:
- `category` — тип Revit (walls, floors, structural_columns, curtain_panels...)
- `family` — семейство (КЖ_Стена_B40..., ВН_Газобетон D600...)
- `type_name` — конкретный типоразмер

Для каждого кластера считаются агрегаты:
- COUNT — количество элементов
- SUM(volume_m3) — суммарный объём
- SUM(area_m2) — суммарная площадь
- SUM(length_m) — суммарная длина
- Зоны, этажи, модели-источники

### Пример кластера:
```
cluster_id: "walls::ВН_Газобетон D600_200мм::ВН_Газобетон D600_200мм"
count: 3361
volume: 4111.50 м3
area: 20617.33 м2
sources: ["BA_AR"]
```

### Результат:
~3000-5000 кластеров — компактное представление 722k элементов.

## Этап 3: Специалисты (LLM-агенты)

**Скрипт:** `bim2vor/reasoning/specialist.py`

```
Кластеры + Позиции ВОР ──→ LLM (Claude) ──→ Аллокации
```

### Кто такие специалисты:
Каждый специалист — один LLM-вызов для своего раздела ВОР. Определены в `recipes/specialists_6_1.yaml`:

| Специалист | Разделы ВОР | Источники BIM |
|-----------|------------|--------------|
| monolith | 04 (нулевой цикл), 05 (надземный монолит) | KR, BA_AR (floors, walls, columns, foundation) |
| masonry | 08 (стены и перегородки) | BA_AR, PR_AR (walls) |
| facades | 06 (ограждающие конструкции) | FC_S1_AR, FC_S2-S3_AR, BA_AR (curtain_panels, windows, walls НР_) |

### Что делает каждый специалист (4 фазы):

**Phase 1 — FILTERING:** Из всех кластеров отбирает свои
```
"walls::ВН_Газобетон D600_200мм::..." → CLAIMED (газобетон = мой раздел 08)
"walls::КЖ_Стена_B40...::..." → REJECTED (ж/б стены = раздел 04/05, не мой)
```

**Phase 2 — COMPLETENESS CHECK:** Проверяет что не пропустил слои/уровни

**Phase 3 — ALLOCATION:** Для каждой позиции ВОР назначает кластеры
```json
{
  "position_id": "08.01.01",
  "quantity": 4111.50,
  "unit": "м3",
  "confidence": 0.90,
  "source_clusters": [
    {"cluster_id": "walls::ВН_Газобетон D600_200мм::...", "share": 1.0}
  ],
  "reasoning": "Газобетон 200мм из BA_AR = vol 4111.50"
}
```

**Phase 4 — DOPNIKI:** Кластеры без позиции → предложить допник

### Результат:
`runs/event_6_1/specialist_outputs/masonry.json`, `monolith.json`, `facades.json`

## Этап 4: Верификация и защита от ошибок

**Скрипт:** `scripts/fill_vor_final.py`

```
Аллокации специалистов ──→ Проверки ──→ Финальные числа
```

### Проверки:

#### 1. Детекция копирования
LLM иногда копирует число заказчика вместо расчёта из BIM.
Детектор: если `|BIM - Заказчик| / Заказчик < 0.1%` → подозрение на копию.

#### 2. DB-верификация
Для каждой аллокации пересчитываем из сырых данных БД:
```python
SELECT SUM(volume_m3) FROM elements 
WHERE category=? AND family=? AND type_name=? AND is_excluded=0
```
Если LLM-число расходится с DB > 5% — используем DB.

#### 3. Sanity check
Если BIM > 10x заказчика и confidence < 0.5 → не заполняем.

#### 4. Нет source_clusters
Если LLM скопировал заказчика и не указал из каких кластеров считал → не заполняем.

### Решения:
- **DB confirms** — DB-пересчёт совпал с LLM (отлично)
- **DB replace** — DB-пересчёт отличается, используем DB (LLM ошибся)
- **Dropped** — нет данных для верификации (не заполняем)
- **Skipped** — qty=0 или conf=0

## Этап 5: Агентный пересчёт (текущий)

**Скрипты:** агенты-Опусы, результаты в `runs/event_6_1/agent_*_result.json`

```
Сырая БД ──→ Агент-сметчик (рассуждает) ──→ Обоснованные объёмы
```

### Отличие от Этапа 3:
- Этап 3: LLM получает готовые кластеры и "раскладывает" их
- Этап 5: Агент **сам** смотрит в БД, **сам** решает какие типы элементов
  соответствуют какой позиции, **рассуждает** о каждом решении

### Принцип работы агента:
1. Запрашивает из БД сводную таблицу: `GROUP BY family, type_name`
2. Читает описание позиции ВОР
3. Рассуждает: "Газобетон D600 200мм = это 08.01.01 (стены из газобетона толщ. 200мм)"
4. Проверяет единицы: ВОР просит м3 → беру `SUM(volume_m3)`, просит м2 → `SUM(area_m2)`
5. Исключает: "Не возводится", "Отделка" (это раздел 09), наружные (это раздел 06)
6. Записывает результат с обоснованием и уровнем уверенности

---

## Этап 6: Запись в Excel

**Скрипт:** `scripts/fill_vor_final.py` (или `bim2vor/report/writer.py`)

```
Финальные числа ──→ openpyxl ──→ vor_comparison.xlsx
```

В колонку 12 (Количество ГП) записывается наше число с цветовой индикацией:
- Зелёный — confidence >= 0.65
- Жёлтый — confidence 0.4-0.65
- Красный — confidence < 0.4

4. Секции C1 vs С2-3 не разделены в БД (нет отдельного поля), определяются через level_raw (S1 vs S2-S3)

## Ключевые принципы

1. **Не верь ВОР заказчика** — наши BIM-числа = truth
2. **Детерминистический пересчёт** — каждое число проверяется SQL-запросом к сырым данным
3. **Явный reasoning** — каждое решение документируется (какой тип → какая позиция и почему)
4. **Лучше пропустить, чем ошибиться** — если нет уверенности, позиция не заполняется
